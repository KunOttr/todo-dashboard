# 现代前端框架（React / Vue）重构评估报告

> 对象：TodoDashboard —— GitHub Issues 待办管理面板（纯静态站点，GitHub Pages 部署）
> 评估日期：2026-09-04
> 方法：源码静态分析 + 框架体积实测（esbuild bundle + minify + gzip，2026-09-04 以 npm latest 安装）
> 数据证据分级：**【实测】**=运行时/文件实测；**【源码】**=直接读代码得出；**【推断】**=经验判断（不确定处已标注）

## 一、结论摘要（TL;DR）

**技术上完全可行，但当前不建议全量重写；推荐「先分层、后决策」的两阶段路线。**

1. **项目的真正复杂度不在 UI，而在「本地优先同步协议层」**（pendingOps 队列 / 乐观更新 / 临时 id→服务端 id 映射 / 401 处理 / 5 分钟 debounce flush）。这层与框架正交，重写时被搬坏的风险最大，而现有 3 套无依赖测试恰好是这层行为的回归保险——全量重写会让这份保险失效。
2. **命令式 DOM 的真实痛点存在且正在逼近临界点**：`app.js` 1,767 行中约七成是渲染模板 + 事件 + 弹窗交互。Roadmap v2 的 P1 梯队（本周视图 / 快速创建 / 周回顾）本质是「多视图 + 各视图筛选状态」——这正是命令式 innerHTML 渲染最吃力的形态。**「是否引框架」应在动手 P1.1（本周视图）之前定案，而不是之后。**
3. **若引框架，Preact / React 优先于 Vue**（对 React 主栈用户学习成本为零、Preact 仅 +4.5 KB gzip）；Vue 3 模板语法与现有 innerHTML 字符串最接近，是第二选择。三者实测体积见第五节——React 19 全家桶 **+60 KB gzip**，比当前全站还重 2.6 倍，是"轻量本地优先"定位的实质负担。
4. **最优中间态：不引框架也能获得大部分收益**——把 `api.js` 之外的数据/状态/同步协议抽成纯 ESM 模块、渲染改为「局部区块更新 + 模板函数化」。这是三条路径共用的第一步，做了不亏，且不阻塞 roadmap。

## 三、复杂度分层：重构时哪些能改、哪些不能碰

对 `app.js` 按函数语义分类（行号区间粗估，边界有交叠）：

```
┌─────────────────────────────────────────────────────────────────┐
│  app.js ≈ 1,767 行                                              │
│                                                                 │
│  ┌───────────────────────────────┐  ┌────────────────────────┐  │
│  │  A. UI/DOM 层  ≈ 1,200 行     │  │ B. 同步协议层 ≈ 300 行 │  │
│  │  render* / cardHTML /         │  │ connect / refresh /    │  │
│  │  editorHTML / 弹窗 / 进度环   │  │ queueOp / execOp /     │  │
│  │  / 事件委托 bindEvents(340)   │  │ flush / optimistic* /  │  │
│  │  / 移动端长按 / 全屏输入       │  │ renderSyncButton       │  │
│  └───────────────────────────────┘  └────────────────────────┘  │
│  ┌───────────────────────────────┐  ┌────────────────────────┐  │
│  │  C. 配置/工具 ≈ 200 行        │  │ D. 设置弹窗 ≈ 130 行   │  │
│  │  loadConfig / AES-GCM 封装    │  │ repo 卡片表单/测试/切换 │  │
│  └───────────────────────────────┘  └────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

- **B 层（协议层）= 最大资产，也是最大风险**。行为契约（队列去重、同类操作合并、flush 顺序、失败回滚、401 语义）是项目经 bug 打磨出来的，与框架无关。全量重写时这里最容易引入隐蔽回归，而现有测试的 DOM 桩恰好不关心 UI、只验证这层——**协议层抽成纯模块后，三套测试几乎可以原样继续跑**。
- **A 层（UI 层）= 框架真正能改善的地方**，但其中隐藏大量非声明式框架默认能力的手工细节：进度 popover 的锚点定位、卡片 3 行截断 + 溢出检测（`textOverflows`）、移动端长按手势 vs 点击二义性、全屏输入编辑器、编辑态与原卡片的显示切换。切框架时这些**交互逻辑要重写而非自动消失**。
- **C/D 层**：C 与框架无关照搬；D 是表单密集型 UI，框架收益最大但优先级最低。

## 四、真实痛点 vs 框架能解决的

| 症状（现在/可预见） | 根因 | 框架能否解决 |
|---|---|---|
| 每加一个筛选/视图维度，就新增一批 `render*` + 状态同步代码，易漏状态 | 状态 → DOM 是手工单向同步，无 diff | ✅ 声明式渲染核心收益。Roadmap P1.1 本周视图（今日/本周/全部/已归档 4 视图）即第一个压测点 |
| 编辑卡片开着时点其他操作，旧卡片显示状态易错乱 | 多处代码各自 mutate 同一 DOM | ✅ 单一数据源 + 重渲染 |
| 新增字段（如 roadmap 的 `due:` / `priority:` 标签字段）要改模板、改事件、改局部刷新 | 字段 → 模板 → 交互分散三处 | ✅ |
| 无 HMR，改 UI 靠手动刷新 | 纯静态无 dev server | ✅ Vite dev server 是真收益（虽非框架本体） |
| innerHTML 拼接靠 escapeHTML 兜底 XSS | 字符串模板天然需要转义 | ✅ JSX / Vue 模板内建转义（迁移后 XSS 面自动收窄） |
| 未来批量操作 / 多选 / 拖拽排序（P2.x） | 命令式做复杂交互成本高 | ✅（React/Vue 均有成熟库） |

**框架解决不了（要清醒）**：协议层复杂度、CORS/混合内容/Token 等平台约束、helpModal 文档维护义务、GitHub Pages 部署模型。这些在任何技术栈下都一样。

## 五、框架选型：实测数据与评分

### 5.1 体积实测（2026-09-04，npm latest，esbuild bundle+minify+gzip，最小可运行 app）

| 方案 | 版本 | min | **gzip** | 相对当前全站 gzip(≈22.9 KB)* | 相对当前业务 JS gzip(≈14 KB) |
|---|:---:|---:|---:|:---:|---:|
| 当前全站（html+css+4js 合并产物） | — | 78 KB | ≈22.9 KB | 基准 | 基准 |
| **Preact** | 10.29.8 | 10.6 KB | **4.5 KB** | +20% | 业务 JS 的 0.3 倍 |
| **Vue 3** | 3.5.42 | 62.7 KB | **25.0 KB** | +109% | 1.8 倍 |
| **React 19（react+react-dom）** | 19.2.8 | 192 KB | **60.1 KB** | +262% | 4.3 倍 |

> *当前全站 gzip 22.9 KB 为 2026-08-22 构建实测（BUILD-ANALYSIS.md），其后 index.html 帮助文档略有增涨（13 KB→18 KB raw），量级不变。
> 结论：体积上 Preact ≪ Vue < React。对「轻量本地优先」定位，React 全家桶的 60 KB gzip 框架开销是实质负担（自用工具可忍，但不再是"轻"）。

### 5.2 选型评分矩阵（1-5 分，越高越好）

| 维度 | Preact | React 19 | Vue 3 | 依据 |
|---|:---:|:---:|:---:|---|
| 团队技能匹配 | 5 | **5** | 3.5 | React 主栈：React API 与 Preact 完全通用；Vue 需适应响应式范式与 SFC |
| 运行时体积 | 5 | 2 | 3.5 | 实测 5.1 |
| 渐进嵌入（局部 mount，协议层不动） | 5 | 4 | 4.5 | Preact/Vue 官方支持局部 mount；React 可用但社区模式偏整树 |
| 从现有代码迁移顺手度 | 3.5 | 3.5 | 4.5 | 现有是字符串模板：Vue 模板（`v-for`/`{{ }}`）直觉最近；JSX/虚拟 DOM 都要重写模板 |
| 声明式收益（视图状态复杂时） | 4.5 | 5 | 5 | 三者等价（同一范式） |
| 生态/测试/长期维护 | 4 | 5 | 4.5 | Preact 兼容 React 生态；React/Vue 测试栈成熟 |
| **加权合计（技能 ×2）** | **26.5** | **26.5** | **24** | — |

**结论**：
- **React 主栈前提下，Preact 与 React 并列最优**——API 一致、技能红利相同，Preact 体积省 13 倍。若不介意 60 KB gzip 且想要最主流生态，直接 React；若在意"轻"，Preact 是 React 的无痛平替（迁移期甚至可以先用 React 写完再换 Preact，或反之，两者 API 兼容）。
- **Vue 3 适合**：想用模板语法渐进替换字符串模板、偏好官方脚手架渐进路线、或想借项目拓宽技术面——代价是放弃 React 技能红利。
- **本轮建议**：若选框架，**优先 Preact（或 React），Vue 作为备选**；决策变量是"技能复用 vs 模板顺手度"，而非技术差距。

## 六、三条路径与里程碑

### 路径 1：先分层、不引框架（**推荐起点**，与后续任何路径兼容）

目标：把"能搬的资产"变成模块，把"决策"推迟到有真实视图需求时。约 2-3 个里程碑，**不阻塞 roadmap P1**。

| 里程碑 | 内容 | 收益 | 大致量级 |
|---|---|---|---|
| M1 模块化 | config/crypto/api/filters 转 ESM；state + 同步协议（pendingOps/flush/optimistic）抽 `core.js` 纯模块；app.js 只留 UI | 协议层可被 Node 直接单测，三套测试保留并强化 | 半天~1 天等效 |
| M2 渲染瘦身 | 现有 `render*` 改为「单一入口 renderAll → 按需局部更新」；模板函数收拢到组件式文件 | 状态同步路径收敛，为视图切换铺路 | 1 天 |
| M3 视图切换骨架 | 顶部视图切换（今日/本周/全部）先以原生实现：视图 = 纯筛选函数，渲染容器化 | 验证痛点是否真到"非框架不可"，收集实证 | 1-2 天 |

> M3 之后：若"视图 = 纯函数 + 局部更新"仍吃力（DOM 泄漏/性能/复杂度），再引框架只重写渲染容器——协议层纹丝不动，测试零失效。**这是把风险控制在最小的决策点。**

### 路径 2：渐进式引框架（若 M3 验证后决定引）

- 构建链：esbuild 手写 → **Vite**（dev HMR + build，产物仍纯静态，GitHub Pages 兼容，`npm run build` 语义不变）。
- 范围：只把「列表视图容器」（区块 + 卡片 + 编辑器）用 Preact/React/Vue 渲染；设置弹窗、标签管理可后续。`core.js`（路径 1 产物）经自定义 hook / composable 暴露。
- 测试：协议层 Node 测试原样保留；新增 UI 层测试选 vitest + jsdom（React: @testing-library/react；Preact: preact-render-to-string / testing-library）。
- 预期：业务 JS 体积 +4.5 KB（Preact）~ +60 KB（React）；功能冻结窗口 1-2 周内的**部分**冻结。

### 路径 3：全量重写 SPA（不推荐当下执行）

- 触发条件（满足其一再评估）：① 协议层稳定 + 功能进入平台期，出现团队/商品化诉求；② UI 状态爆炸到原生确实不可维护（如 10+ 视图、复杂拖拽）；③ 需要 PWA/离线完整化等工程化能力。
- 成本诚实预估：个人开发者业余节奏下 3-5 周全量重写 + 测试重建，期间与 roadmap P1 抢时间——**当下（P1 尚未动工）是"最不该全量重写"的时点，因为功能面还在扩张**。
- 若未来全量重写：React+Vite+TS+vitest 是主流默认；数据层直接搬 `api.js`/`core.js`，UI 全新实现。

## 七、风险清单（P0 / P1 / P2）

### P0 — 无阻断，但必须设计先行

| 风险 | 说明 | 缓解 |
|---|---|---|
| 协议层回归 | flush 顺序/队列合并/乐观回滚/401 语义是 bug 打磨产物 | 路径 1 先抽 core 并保持三套测试跑通，再谈 UI |
| 测试资产失效 | 现有测试 = eval 注入 + 自写 DOM 桩，对框架 UI 不适用 | 协议层 Node 测试保留；UI 测试仅覆盖新增组件，不强求 1:1 迁移 |

### P1 — 需要流程保障

| 风险 | 说明 | 缓解 |
|---|---|---|
| 交互细节丢失 | 移动端长按 vs 点击、进度 popover 锚点定位、3 行截断溢出检测、全屏编辑器，都是手写细节 | 迁移时逐条列验收清单（现有 helpModal 可作 spec 源） |
| helpModal 文档义务 | 项目约定功能改动必同步帮助文档——重构本身不改功能，但重写 UI 时易忘 | 把"同步帮助文档"写进迁移验收清单 |
| 双轨期双源维护 | 框架分支与原生分支并行时改功能的双份成本 | 迁移期冻结新功能（与 roadmap P1 排期错开） |
| 平台分支逻辑 | GHE GraphQL 端点拼接、混合内容、Gitea CORS、401 提示文案 | 全部在 api.js/core.js，禁止散落到 UI 组件 |

### P2 — 体验与细节

| 风险 | 说明 | 缓解 |
|---|---|---|
| 体积/首屏 | React +60 KB gzip | Preact 或接受（自用工具） |
| 无障碍/键盘 | 现有无系统化 a11y，迁移是补课机会 | 组件化后逐项补 aria/label |
| 历史迁移遗留 | `localStorage` 旧格式（全局 useProgress→per-repo）迁移逻辑 | 已在 loadConfig，属 C 层，勿重写 |

## 八、决策建议

| # | 决策点 | 建议 |
|---|---|---|
| 1 | 现在全量重写？ | ❌ 不做。功能扩张期 + 协议层是重写风险区 + 测试资产会失效 |
| 2 | 现在引框架？ | ⏸ **推迟到 P1.1（本周视图）设计前定案**——它是第一个"多视图"功能，是框架收益的压测点，也是最后的不阻塞窗口 |
| 3 | 近期该做什么？ | ✅ 路径 1 M1-M2（分层 + 渲染瘦身），约 2-3 天等效投入，测试资产保留，与 roadmap 不冲突 |
| 4 | 若引，选谁？ | Preact（=React API，+4.5 KB）或 React（+60 KB，最主流）；Vue 3 为模板范式备选 |
| 5 | 体积底线 | 若坚持"轻量本地优先"叙事，≤25 KB gzip 增量（Vue/Preact 区间），React 需理由 |
| 6 | 测试策略 | 协议层永远 Node 直测；UI 层若引框架用 vitest+jsdom，否则手工冒烟 + helpModal 清单 |

**一句话**：这个项目值钱的不是 UI，是同步协议；UI 的痛点真实存在但还没爆。先用 2-3 天把架构分好层、把决策点推到"本周视图"之前，届时带着实证（视图切换是否真的拖垮原生渲染）再定框架——届时选 React/Preact/Vue 都是半小时内的迁移，因为协议层已独立。
